# Архитектура

## Общая схема

```
MainActivity ──> KopeechkaRoot (Compose)
      │                │
      │                ├── HomeScreen / OpsScreen / BudgetScreen / ReportScreen
      │                ├── SettingsScreen + страницы (счета, категории, цели, валюты, копия)
      │                └── оверлеи (операция, ИИ-советник, редакторы, нижние листы)
      │
      └──> AppViewModel ──> Store (JSON-файл) ──> StateFlow<AppData>
                    │
                    ├──> Calc          расчёты поверх AppData
                    ├──> SecureStore   API-ключи в Android Keystore
                    ├──> Ai            Claude / OpenAI / Gemini / свой endpoint
                    └──> DriveBackup   Google Drive REST v3
```

Слоёв ровно три: данные (`data/`), внешние сервисы (`net/`), интерфейс (`ui/`).
Фоновые задачи живут отдельно в `work/`.

## Данные

Всё состояние приложения — один неизменяемый объект `AppData`: счета, категории,
операции, цели, настройки. Он лежит в одном JSON-файле во внутреннем хранилище
(`files/kopeechka.json`) и раздаётся интерфейсу через `StateFlow`.

**Почему не Room.** Объём данных личных финансов невелик — тысячи операций, это сотни
килобайт. Один файл даёт три преимущества: резервная копия совпадает с форматом хранения
(тот же JSON уходит в Google Диск), нет миграций схемы при добавлении полей (новые поля
получают значения по умолчанию, `ignoreUnknownKeys` терпит старые), и всё состояние
доступно синхронно, без корутин на каждый чтение.

Запись атомарная: `AtomicFile` пишет во временный файл и подменяет основной, поэтому
прерывание на середине не портит данные. Сама запись уходит в отдельный поток,
чтение всегда из памяти.

### Балансы считаются, а не хранятся

У счёта есть только `initial` — стартовый остаток. Текущий баланс выводится:

```
balance(счёт) = initial + Σ (суммы операций по счёту) + Σ (зачисления переводов)
```

Поэтому редактирование и удаление операции автоматически исправляют баланс — нет
состояния, которое могло бы разойтись с историей. Цена — пересчёт при каждом обращении,
но при таких объёмах он незаметен.

### Переводы и взносы на цель

Это не отдельные сущности, а операции со служебными категориями `transfer` и `goal`:

- перевод: `amount` отрицательная по счёту-источнику, `toAcc` и `toAmount` — куда и сколько
  зачислено (валюты пересчитываются по курсу);
- взнос на цель: списание со счёта плюс ссылка `goal` на цель.

`Calc.isReal()` отсекает их из доходов и расходов, чтобы перекладывание денег между
своими счетами не выглядело тратой.

## Расчёты (`Calc`)

`Calc` — тонкая обёртка над `AppData` с датой «сегодня». Создаётся на каждую отрисовку,
ничего не кеширует между кадрами (внутри — `by lazy` на тяжёлые агрегаты). Отвечает за:

- конвертацию валют (база — рубль, курсы хранятся в настройках);
- балансы, месячные бюджеты, свободные деньги;
- периоды отчётов: `range(period, offset)` возвращает календарный отрезок
  (неделя, месяц, квартал, год) со сдвигом назад;
- разрезы `breakdown()` и столбики `series()`;
- сравнение с прошлым периодом `compare()` — за тот же отрезок, чтобы текущий незаконченный
  месяц сравнивался с таким же куском прошлого;
- цвета категорий (свой из палитры либо запасной по позиции).

## Интерфейс

Jetpack Compose без навигационной библиотеки: экран — это поле `tab`/`page` во ViewModel,
оверлеи — nullable-поля (`draft`, `accEdit`, `curSheet` …). Системная кнопка «назад»
обрабатывается одним методом `AppViewModel.back()`, который закрывает верхний слой.

Оформление берётся из дизайн-системы Industry и живёт в `ui/theme/Theme.kt`:
`KopeechkaColors` — токены светлой и тёмной темы, раздаются через `CompositionLocal`.
Material3 используется только как источник примитивов (`Text`, `Icon`), вся визуальная
грамматика своя: квадратные углы, волосяные рамки, метки «+» по углам (`Modifier.blueprintMarks`).

Шрифты: Barlow и Barlow Condensed. Кириллицы в них нет, поэтому на Android 10+
собирается `Typeface.CustomFallbackBuilder` с системным `sans-serif-condensed` —
латиница и цифры идут узким Barlow, кириллица подхватывается системным узким шрифтом.

## Языки

Переводы лежат не в `strings.xml`, а в трёх картах «ключ → строка» (`data/Lang.kt`,
`LangEn.kt`, `LangTk.kt`). Причина — язык переключается внутри приложения и должен менять
не только интерфейс, но и данные: названия валют, месяцы, разделители чисел, тексты запроса
к ИИ и демо-данные. Ресурсы Android так не умеют без пересоздания Activity.

- `Lang.t("key", arg)` подставляет `{0}`, `{1}`; `Lang.pl(n, "day")` выбирает форму
  множественного числа (в русском три формы, в английском две, в туркменском одна).
- Пропущенный ключ откатывается по цепочке `tk → en → ru`, поэтому неполный перевод
  не оставляет пустых мест.
- В Compose язык раздаётся через `LocalLang`, короткая форма — `T.l`.
- Вне Compose язык берётся из настроек: `AppViewModel.l`, `Calc.l`, `Currencies.lang`.
- В `strings.xml` осталась одна строка — имя приложения в лаунчере (там нужны именно ресурсы).

## Внешние сервисы

**ИИ-советник** (`net/Ai.kt`). Claude вызывается официальным Java SDK Anthropic,
остальные провайдеры — прямым HTTP через OkHttp. Запрос собирается из данных,
которые пользователь сам отметил галочками. Без ключа работает офлайн-разбор —
те же выводы, посчитанные локально по правилам.

**Резервные копии** (`net/DriveBackup.kt`). Google Drive REST v3, область `drive.file`:
приложение видит только созданные им файлы. Токен берётся через
`Identity.getAuthorizationClient`, файлы кладутся в папку «Копеечка — резервные копии».

**Фон** (`work/Workers.kt`). WorkManager: ежедневная копия по Wi-Fi и вечернее напоминание.

## Что намеренно не сделано

- Нет DI-фреймворка: две зависимости создаются в `Application` и передаются вручную.
- Нет репозиториев и use-case'ов поверх `Store` — на таком объёме это лишний слой.
- Нет автоматической загрузки курсов валют: они задаются вручную, приложение не требует сети.
